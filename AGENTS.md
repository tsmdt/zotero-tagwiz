# AGENTS.md

Guidance for coding agents working on TagWiz, a Zotero 7+ plugin (developed
and tested on Zotero 10.0.6) for bulk tag cleanup: change case, rename/merge,
remove, merge duplicates, and undo/redo through a History tab. User-facing
behavior is documented in `README.md`; read it before changing behavior.

## Safety first

TagWiz does library-wide writes to a user's research database. Silent data
changes are the worst kind of bug here.

- Never point development or tests at a live Zotero profile or data directory.
  `.env` must name a separate development profile (see `.env.example`).
- Every write goes through `src/zotero/engine.ts`, which checks `preflight()`
  (`src/zotero/guard.ts`) and writes an undo journal _before_ the first change.
  Don't add write paths that bypass the engine or the journal.
- Tag edits must not touch an item's "Date Modified": keep using
  `SAVE_OPTIONS` (`skipDateModifiedUpdate`, `skipEditCheck`) in the engine.
- Tag names are compared after `cleanName()` (NFC + trim), as Zotero stores
  them. A name can exist both as a manual (type 0) and an automatic (type 1)
  tag; Zotero's tag APIs are keyed by name, which is why ops on `TagRef`s are
  folded into name-level `Task`s (`src/core/tasks.ts`).

## Layout

| Path                                           | Contents                                                                                                                         |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `src/core/`                                    | Pure logic, no Zotero globals: case styles, duplicate keys, plans, tasks, history chains. Unit-tested in plain Node.             |
| `src/zotero/`                                  | Zotero I/O: `tagStore` (SQL reads, snapshots), `engine` (apply/undo/redo), `journal` (snapshots in `<dataDir>/tagwiz`), `guard`. |
| `src/ui/`                                      | The dialog. `dialog.ts` is the whole window (large); `dom.ts` has the `h()` element builder; `openDialog.ts` opens/focuses it.   |
| `src/modules/menus.ts`                         | Tools menu and collection context menu (`Zotero.MenuManager`, with a legacy fallback).                                           |
| `src/hooks.ts`, `src/addon.ts`, `src/index.ts` | Plugin lifecycle, from the Zotero Plugin Template.                                                                               |
| `addon/`                                       | Static files: `manifest.json`, `bootstrap.js`, `content/dialog.xhtml` + `dialog.css`, Fluent strings in `locale/en-US/*.ftl`.    |
| `typings/`                                     | `i10n.d.ts` and `prefs.d.ts` are generated by zotero-plugin-scaffold on build; don't edit them by hand.                          |
| `test/unit/`                                   | Mocha + chai unit tests for `src/core` (and `src/ui/dom.ts`).                                                                    |
| `test/*.test.ts`                               | Integration tests that run inside Zotero (`engine`, `dialog`, `startup`).                                                        |
| `reports/`                                     | Audit reports (gitignored). Useful background on past bugs and their fixes.                                                      |

Keep anything that can be pure in `src/core/` so it stays unit-testable.
`src/core/` must not reference `Zotero`, `ztoolkit` or `addon`.

## Commands

Node 24 (`.nvmrc`).

| Command              | What it does                                                                   |
| -------------------- | ------------------------------------------------------------------------------ |
| `npm start`          | Build, start Zotero with the plugin (needs `.env`), reload on change           |
| `npm run build`      | Production build to `.scaffold/build/*.xpi`, then type-checks `src` and `test` |
| `npm run test:unit`  | Unit tests in plain Node (`mocha --import=tsx`)                                |
| `npm test`           | All tests inside Zotero (needs a Zotero binary)                                |
| `npm run lint:check` | Prettier + ESLint; `npm run lint:fix` to fix                                   |

CI (`.github/workflows/ci.yml`) runs lint, unit tests, build and the Zotero
tests on every PR to `main`. Run at least type check, lint and unit tests
before you call a change done.

### Running checks in the Linux sandbox

`node_modules` is installed on the macOS host (`@esbuild/darwin-arm64` only),
so anything that uses esbuild (`tsx`, `npm run test:unit`, `npm run build`,
`npm start`) fails in a Linux sandbox. **Don't reinstall `node_modules` in
place without asking the user.** These work instead:

```sh
# Type check
node node_modules/typescript/bin/tsc --noEmit
node node_modules/typescript/bin/tsc --noEmit -p test

# Lint
node node_modules/prettier/bin/prettier.cjs --check .
node node_modules/eslint/bin/eslint.js .

# Unit tests: compile with tsc to CommonJS in a scratch dir, run mocha there
OUT=<scratch dir>
node node_modules/typescript/bin/tsc --outDir $OUT --module commonjs \
  --moduleResolution node --target es2022 --skipLibCheck --esModuleInterop \
  --types mocha,node --rootDir . src/core/*.ts test/unit/*.ts
echo '{"type":"commonjs"}' > $OUT/package.json
NODE_PATH=$PWD/node_modules node node_modules/mocha/bin/mocha.js "$OUT/test/unit/*.test.js"
```

The Zotero integration tests cannot run in the sandbox; say so and ask the
user to run `npm test` on the host when a change touches `src/zotero/` or
`src/ui/`.

## Conventions

- TypeScript, Prettier defaults (80 columns, 2 spaces, LF). The ESLint config
  is `@zotero-plugin/eslint-config`.
- Comments explain _why_ and point to the Zotero behavior they rely on
  (e.g. "see Zotero.Tags.cleanData"). Public functions and non-obvious fields
  get a short JSDoc comment. Match this density.
- All user-visible text goes in `addon/locale/en-US/addon.ftl` and is read
  with `getString()` / `getLocaleID()` (`src/utils/locale.ts`). Keep each
  string's wording consistent with the README.
- Build the dialog's DOM with `h()` from `src/ui/dom.ts`; style it in
  `addon/content/dialog.css` and keep dark mode working.
- `addon/content/dialog.xhtml` is excluded from Prettier: its processing
  instructions must stay one per line.
- Long-running work is chunked (`ITEM_CHUNK`, `CHUNK`) so large libraries
  don't block the UI or hit SQL parameter limits; keep that when adding loops
  over items or tags.
- Journals: the last 10 runs per library are kept (at most 50 files).
  Journals written by older versions lack newer fields (e.g. `kind`); keep
  reading them (see `editKindOf`).

## Tests

- Add or update unit tests in `test/unit/` for any change to `src/core/`.
- Changes to the engine, journal or dialog need integration tests in
  `test/engine.test.ts` / `test/dialog.test.ts`.
- When fixing a bug, add a test that fails without the fix.

## Docs and commits

- When behavior changes, update `README.md` in the same change. It is written
  for end users: concrete examples, plain language, no internals.
- Branches: `feature/<name>` or `fix/<name>`, PRs to `main`.
- Commit subjects: `feat: …`, `fix: …`, `chore: …`, imperative, lower case.
- Releases are done by the maintainer (`npm run release`, tag `v*` triggers
  `.github/workflows/release.yml`). Don't bump the version or tag a release
  unless asked.
